# ADR-0009: Vercel-Native Registry with Analytics

## Status

Rejected — explored but decided against. Vercel Pro required for custom events, and GitHub Releases already provides download counts for free. Registry page uses SSR to fetch registry.json from GitHub Releases instead.

## Context

olore has grown to 70 documentation packages. The current registry (`registry.json` on GitHub Releases + `olore.dev/registry/index.json` fallback) was last updated March 8 and is missing 29 packages. There is:

1. **No browsable registry** — Users can only discover packages via `olore search` (CLI) or reading the repo
2. **No download tracking** — Tarballs are served directly from GitHub Releases with no visibility into usage
3. **No visit analytics** — olore.dev has no instrumentation

### Design constraint

The maintainer explicitly prefers **a single platform** over mixing multiple products (PostHog, Upstash, Neon, etc.). Even a few dollars/month is acceptable if it means staying within one ecosystem and reducing cognitive overhead. Vercel is already the deployment platform and has all the primitives needed.

### Relationship to ADR-0005

ADR-0005 ("Registry Generation at Build Time") covers how `registry.json` is generated from `olore-lock.json` files and how tarballs are published to GitHub Releases. That ADR remains valid and is a prerequisite. This ADR extends it with:

- A browsable registry UI
- Download tracking via Vercel Analytics
- A download API route that enables analytics without changing the tarball hosting

## Decision

**Host the entire registry experience on Vercel using only Vercel-native products.**

### Architecture

```
┌─────────────────────────────────────────────────────────────┐
│  olore.dev (Next.js on Vercel)                              │
│                                                             │
│  /registry              → SSG browse page (all packages)    │
│  /registry/[name]       → SSG detail page (per package)     │
│  /api/download/:name/:v → API route (track + 302 redirect)  │
│                                                             │
│  Static assets:                                             │
│  /registry/registry.json → Generated at build time (ADR-0005)│
│                                                             │
│  Analytics:                                                 │
│  @vercel/analytics       → Page visits (automatic)          │
│  @vercel/analytics       → Download events (custom)         │
└─────────────────────────────────────────────────────────────┘
        │                           │
        │ 302 redirect              │ track()
        ▼                           ▼
┌───────────────────┐     ┌───────────────────┐
│  GitHub Releases  │     │  Vercel Analytics  │
│  (tarball hosting)│     │  Dashboard         │
│  ├── *.tar.gz     │     │  ├── Page views    │
│  └── *.sha256     │     │  ├── Downloads     │
└───────────────────┘     │  └── By package    │
                          └───────────────────┘
```

### Components

#### 1. Registry Pages (SSG)

Static pages generated at build time from `registry.json`:

- **`/registry`** — Browse all packages with client-side search/filter
- **`/registry/[name]`** — Package detail (description, versions, file count, install command)

Data source: `registry.json` generated by existing `web/scripts/generate-registry.ts` (ADR-0005).

Pages are fully static (SSG via `generateStaticParams`). No database, no server-side rendering. Rebuild on each deploy picks up new packages automatically.

#### 2. Download API Route

```
GET /api/download/:name/:version
  → Track custom event via @vercel/analytics
  → 302 redirect to GitHub Releases tarball URL
```

This is the only server-side component. It:
1. Looks up the tarball URL from the build-time `registry.json`
2. Fires a Vercel Analytics custom event: `track('download', { package: name, version })`
3. Returns a 302 redirect to the GitHub Releases URL

The actual file serving remains on GitHub's CDN. Vercel only handles the redirect (~50ms overhead).

#### 3. Vercel Analytics

Single product handles both needs:

| Metric | How | Dashboard |
|--------|-----|-----------|
| Page visits | `@vercel/analytics` automatic tracking | Vercel Analytics → Web |
| Download counts | `track('download', { package, version })` custom event | Vercel Analytics → Custom Events |

**Hobby plan limits:** 25K custom events/month. At current scale (estimated <1K downloads/month), this is more than sufficient.

#### 4. CLI Integration

Update CLI to route downloads through the API:

```typescript
// cli/src/core/constants.ts
// downloadUrl in registry.json changes from:
//   https://github.com/olorehq/olore/releases/download/prisma@latest/prisma-latest.tar.gz
// to:
//   https://olore.dev/api/download/prisma/latest
//
// The API route 302-redirects to the GitHub Releases URL.
// CLI follows the redirect transparently.
```

Alternatively, keep `downloadUrl` pointing to GitHub directly and have the CLI fire a non-blocking analytics ping to `/api/track` before downloading. This avoids adding latency to installs.

**Recommended approach:** Non-blocking ping. The CLI sends a fire-and-forget POST to `/api/track` with `{ package, version }`, then immediately starts downloading from GitHub. Zero latency impact, full analytics.

### Search

Client-side only. The `registry.json` for 70 packages is ~50-100KB. Load it once, filter in the browser with a simple text input matching against package name and description. No server-side search needed.

### Cost

| Component | Vercel Product | Monthly Cost |
|-----------|---------------|-------------|
| Hosting (SSG pages) | Vercel Platform | $0 |
| Download API route | Serverless Functions | $0 (100K/mo free) |
| Page visit tracking | Vercel Analytics | $0 (included) |
| Download event tracking | Vercel Analytics Custom Events | $0 (25K/mo free) |
| Tarball storage | GitHub Releases (unchanged) | $0 |
| **Total** | | **$0/month** |

Pro plan ($20/mo) only needed if: >100GB bandwidth/mo, >100K function invocations/mo, or >25K custom events/mo.

## Implementation Plan

### Phase 1: Analytics (quick win)

1. `pnpm add @vercel/analytics` in `web/`
2. Add `<Analytics />` to `layout.tsx`
3. Page visit tracking is now live

### Phase 2: Download tracking

1. Create `web/src/app/api/track/route.ts` — accepts POST with `{ package, version }`, fires `track()` event
2. Update CLI to send non-blocking ping on install
3. Download counts visible in Vercel Analytics dashboard

### Phase 3: Registry pages

1. Create `web/src/app/registry/page.tsx` — SSG browse page reading from generated `registry.json`
2. Create `web/src/app/registry/[name]/page.tsx` — SSG detail page with `generateStaticParams`
3. Add client-side search component
4. Show download counts (pulled from Vercel Analytics API at build time, or displayed as "analytics available in dashboard" initially)

### Phase 4: Registry freshness

1. Accept ADR-0005 and implement `generate-registry.ts` improvements
2. Create GitHub Action for tarball publishing
3. All 70 packages appear in registry

## Consequences

### Positive

- **Single platform** — Everything on Vercel, one dashboard, one billing
- **Zero cost** — Well within Hobby tier limits
- **No ops burden** — No databases, no Redis, no external services
- **SSG performance** — Registry pages are static, edge-cached, instant
- **Analytics built-in** — Vercel Analytics is native, no third-party JS
- **Simple mental model** — Build time generates registry, runtime tracks events

### Negative

- **25K event cap** — If downloads exceed 25K/month, need Pro ($20/mo)
- **No real-time counters on pages** — Download counts require Vercel Analytics API (or just "view in dashboard")
- **GitHub Releases dependency** — Tarballs still hosted externally (but this is already the case per ADR-0004)

### What we explicitly chose NOT to do

- **Upstash Redis for counters** — Adds a second product for marginal benefit
- **Neon Postgres for download history** — Overkill for simple counters
- **PostHog for analytics** — Powerful but adds another platform to manage
- **Vercel Blob for tarballs** — GitHub Releases is free and already works
- **Server-side search** — 70 packages doesn't justify it
